# 代码质量把控实施文档

本文是一份可从零执行的前端项目代码质量实施指南。示例以 **Node.js + pnpm + TypeScript + React/Vite + VS Code + Git** 为基础；其他 JavaScript/TypeScript 项目可以保留通用步骤，并按实际框架调整 TypeScript 检查和构建命令。

实施完成后，项目将具备：ESLint 静态检查和自动修复、TypeScript 类型检查、暂存文件自动修复、统一提交信息校验、提交前检查、推送前构建，以及 VS Code 保存时修复代码和显示括号层级引导线。

> 所有命令均从项目根目录运行。开始前，先确认项目已有 `package.json`、Git 仓库和可用的构建命令。如果项目使用 npm 或 Yarn，将 `pnpm` 替换为相应包管理器命令，并避免混用多个 lockfile。

## 一、准备项目和开发环境

### 步骤 1：确认环境及项目结构

```bash
node --version
pnpm --version
git status
```

若尚未初始化 Git 仓库，先执行：

```bash
git init
```

安装项目现有依赖：

```bash
pnpm install
```

推荐新项目使用 TypeScript。已有 JavaScript 项目也可以照常配置 ESLint、格式化、Git hooks 和提交信息校验，跳过 TypeScript 类型检查相关步骤即可。

### 步骤 2：确定质量门禁

先决定每次提交和推送分别必须通过哪些检查，避免开发者无法预期提交耗时。本指南采用以下分层：

| 时机          | 检查                              | 目的                                 |
| ------------- | --------------------------------- | ------------------------------------ |
| 编辑器保存    | ESLint 可自动修复的问题           | 尽早修复本地代码问题、统一格式       |
| 每次提交前    | 暂存文件自动修复 + 全项目类型检查 | 避免提交明显的代码错误               |
| 提交信息校验  | Commitlint                        | 确保历史记录格式一致                 |
| 每次推送前    | 项目构建                          | 避免推送无法构建的代码               |
| 开发者手动/CI | 自动化测试、受影响功能验证        | 发现静态检查和构建无法覆盖的行为问题 |

测试和覆盖率依赖项目实际使用的测试框架。没有配置测试脚本时，不要把 `pnpm test` 添加为必跑门禁；先安装并配置真实的测试运行器。

## 二、安装静态检查工具

### 步骤 3：安装 ESLint、TypeScript 和 Git hooks 依赖

TypeScript + React 项目可以运行：

```bash
pnpm add -D eslint @antfu/eslint-config typescript typescript-eslint \
  husky lint-staged \
  @commitlint/cli @commitlint/config-conventional \
  prettier prettier-plugin-tailwindcss
```

如果终端不支持反斜杠换行，将命令写成一行。如果项目已经安装其中某项开发依赖，可省略已安装项。

这些工具的分工如下：

- **ESLint**：发现代码问题并应用支持的自动修复规则。
- **TypeScript**：检查类型错误及配置中启用的严格规则。
- **lint-staged**：只对 Git 暂存区中的匹配文件运行指定命令。
- **Husky**：将检查接入 Git 提交和推送生命周期。
- **Commitlint**：校验提交说明。
- **Prettier**：格式化 Markdown、JSON 和样式等指定类型文件。
- **prettier-plugin-tailwindcss**：格式化带 Tailwind CSS 类名的文件时，按统一规则排序类名。

> 本实施方案由 ESLint 管理 JS/TS 代码格式，由 Prettier 管理 Markdown、JSON、CSS/SCSS 等文件，避免两个格式化器同时争夺同一类代码文件。

### 步骤 4：创建 ESLint Flat Config

在项目根目录创建 `eslint.config.js`：

```js
import antfu from "@antfu/eslint-config";

export default antfu({
  react: true,
  typescript: true,
  stylistic: {
    indent: 2,
    quotes: "single",
    braceStyle: "stroustrup",
  },
  ignores: ["dist/**", "coverage/**", "src/components/generated/**"],
});
```

按照自己的项目调整忽略路径，例如生成代码、构建产物或不希望手动改动的第三方组件目录。**不要照搬示例中的生成代码路径**，除非项目确实存在该目录。避免用范围过大的忽略规则，让项目自己的源码退出检查。

如果项目不使用 React，删除 `react: true`；如果项目不使用 TypeScript，删除 `typescript: true` 和 `typescript-eslint` 依赖。配置应与实际代码语言及框架一致。

在 `package.json` 的 `scripts` 中添加或合并以下脚本，保留项目已有的其他脚本：

```json
{
  "scripts": {
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "typecheck": "tsc --noEmit"
  }
}
```

如果项目使用 Vite 的 TypeScript project references，类型检查可根据项目配置改成 `tsc -b`；确保命令实际检查应用源码和构建配置，不要仅凭命令名称判断覆盖范围。没有 TypeScript 的项目删除 `typecheck` 脚本即可。

运行 ESLint 检查：

```bash
pnpm lint
```

尝试自动修复支持的规则：

```bash
pnpm lint:fix
```

检查自动修复后的改动：

```bash
git diff
```

首先修复配置和代码本身的问题，再继续安装提交门禁。不要为了让检查变绿就无理由禁用规则或大范围排除源码目录。

### 步骤 5：启用 TypeScript 严格检查

TypeScript 项目检查 `tsconfig.json`、应用配置及构建工具配置。对于适用于项目的配置，开启严格检查并排查编译错误：

```jsonc
{
  "compilerOptions": {
    "strict": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noFallthroughCasesInSwitch": true,
  },
}
```

如果当前 `tsconfig.json` 是项目引用根配置，勿直接将此片段覆盖进去；应把选项加到实际包含源码的应用配置中。迁移现有项目时可以先检查并修复新增错误，再将严格检查纳入提交门禁。不要用放宽类型或删除必要类型的方式掩盖真实问题。

先运行项目对应的类型检查命令，例如：

```bash
pnpm typecheck
```

### 步骤 6：设置 Prettier 配置和格式化脚本

在根目录创建 `.prettierrc.json`：

```json
{
  "singleQuote": true,
  "semi": false,
  "printWidth": 100,
  "plugins": ["prettier-plugin-tailwindcss"]
}
```

此处的宽度、引号、分号等选项是可供团队选择的示例；团队应协商后保持稳定。插件可以整理其支持文件中的 Tailwind 类名，不使用 Tailwind 时可以移除插件及对应配置。

在 `package.json` 的 `scripts` 中添加或合并：

```json
{
  "scripts": {
    "format": "prettier --write \"**/*.{md,json,css,scss,less}\"",
    "format:check": "prettier --check \"**/*.{md,json,css,scss,less}\""
  }
}
```

确认 glob 与项目目录和文件类型匹配。Prettier 默认会跳过 `node_modules` 等目录；如果仓库中还有大型生成目录，应通过 `.prettierignore` 排除它们。例如创建 `.prettierignore`：

```text
node_modules/
dist/
coverage/
src/components/generated/
```

仅在项目确实存在相应生成目录时添加最后一条忽略规则。运行格式检查和格式化：

```bash
pnpm format:check
pnpm format
```

修改后查看 `git diff`，确保没有将大范围无关格式变更混入业务提交。

## 三、自动检查暂存文件并统一提交信息

### 步骤 7：配置暂存文件任务

在项目根目录创建 `lint-staged.config.cjs`：

```js
module.exports = {
  "*.{js,jsx,ts,tsx}": ["eslint --fix"],
  "*.{css,scss,less,json,md}": ["prettier --write"],
};
```

文件类型和命令应根据项目实际支持的语言调整：

- JS/TS 文件使用 ESLint 检查和自动修复。
- Prettier 负责 Markdown、JSON、CSS/SCSS 等不由 ESLint 管理的格式。
- ESLint 任务只匹配 ESLint 确实能够处理的文件；不要把 CSS 加入任务，却未安装或配置 CSS 检查器。
- 如有 `.vue`、`.html` 或其他文件类型，先验证对应工具及 parser 已正确配置，再增加 glob。

### 步骤 8：启用 Husky 并创建 Git hooks

初始化 Husky：

```bash
pnpm exec husky init
```

确认初始化后 `package.json` 包含安装脚本：

```json
{
  "scripts": {
    "prepare": "husky"
  }
}
```

如果缺少该脚本，手动将其并入 `package.json` 的 `scripts`。之后运行 `pnpm install` 会执行 `prepare`，为当前仓库安装 hooks。

在 `.husky/pre-commit` 中写入：

```sh
pnpm exec lint-staged && pnpm typecheck
```

如果项目没有 TypeScript，将内容改为：

```sh
pnpm exec lint-staged
```

在 `.husky/commit-msg` 中写入：

```sh
pnpm exec commitlint --edit "$1"
```

在 `.husky/pre-push` 中写入：

```sh
pnpm build
```

将 `pnpm build` 换成项目真实的生产构建脚本。如果项目没有生产构建流程，改为实际存在的验证命令，并清楚记录原因。不要调用并不存在的测试脚本。Husky hook 应具有可执行权限；如果文件已经由 Husky 正确生成，保留其原有头部和格式，只修改命令部分。

> Git hooks 可被开发者显式跳过，因此 hooks 是本地快速反馈，不是无法绕过的安全边界。需要对所有分支强制执行的检查，还应放在项目实际使用的 CI 和分支保护规则中。

### 步骤 9：配置 Commitlint 提交信息规则

在根目录创建 `commitlint.config.cjs`：

```js
module.exports = {
  extends: ["@commitlint/config-conventional"],
  rules: {
    "type-enum": [
      2,
      "always",
      [
        "feat",
        "fix",
        "docs",
        "style",
        "refactor",
        "perf",
        "test",
        "chore",
        "revert",
      ],
    ],
    "subject-case": [0],
    "type-empty": [2, "never"],
    "subject-empty": [2, "never"],
  },
};
```

提交信息格式：

```text
<type>(<可选 scope>): <简短、明确的主题>
```

| 类型       | 用途                           |
| ---------- | ------------------------------ |
| `feat`     | 增加功能                       |
| `fix`      | 修复问题                       |
| `docs`     | 文档变更                       |
| `style`    | 不改变逻辑的代码格式调整       |
| `refactor` | 重构                           |
| `perf`     | 性能优化                       |
| `test`     | 测试相关改动                   |
| `chore`    | 工具、依赖、构建等其他维护事项 |
| `revert`   | 回滚                           |

例如：

```text
feat(auth): 增加登录验证码
fix: 修复登录页面按钮状态
refactor(router): 简化动态路由处理
docs: 补充项目配置说明
```

`scope` 可选，主题必填。上述 `subject-case` 规则允许中文主题；类型仍必须来自允许列表。团队如需强制主题使用特定语言，应另行统一规则。提交前钩子会拒绝不符合规则的提交说明。

## 四、配置 VS Code 保存修复和可读的代码块

### 步骤 10：安装必要的编辑器扩展

在 VS Code 扩展面板安装 Microsoft 发布的 **ESLint** 扩展。团队可通过 `.vscode/extensions.json` 推荐扩展：

```json
{
  "recommendations": ["dbaeumer.vscode-eslint", "esbenp.prettier-vscode"]
}
```

本方案中 JS/TS 使用 ESLint 保存修复，Markdown、JSON 和样式通过 Prettier 命令及提交前钩子格式化。可以安装 Prettier 扩展方便手动格式化文档，但不要让 Prettier 同时重排 JS/TS，而与 ESLint 争夺代码格式。

### 步骤 11：添加团队共享 VS Code 设置

在项目根目录创建 `.vscode/` 文件夹，并在其中创建 `settings.json`。也可以在 VS Code 打开项目后，通过命令面板运行 **Preferences: Open Workspace Settings (JSON)** 创建工作区设置。将以下配置作为团队共享的工作区设置：

```jsonc
{
  "eslint.useFlatConfig": true,
  "eslint.validate": [
    "javascript",
    "javascriptreact",
    "typescript",
    "typescriptreact",
  ],
  "editor.formatOnSave": true,
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit",
    "source.organizeImports": "never",
  },
  "editor.guides.bracketPairs": "active",
  "editor.tabSize": 2,
  "editor.insertSpaces": true,
  "[javascript]": {
    "editor.defaultFormatter": "dbaeumer.vscode-eslint",
  },
  "[javascriptreact]": {
    "editor.defaultFormatter": "dbaeumer.vscode-eslint",
  },
  "[typescript]": {
    "editor.defaultFormatter": "dbaeumer.vscode-eslint",
  },
  "[typescriptreact]": {
    "editor.defaultFormatter": "dbaeumer.vscode-eslint",
  },
  "[markdown]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode",
  },
  "[json]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode",
  },
  "[css]": {
    "editor.defaultFormatter": "esbenp.prettier-vscode",
  },
}
```

此配置让 ESLint 负责 JS/JSX/TS/TSX 的保存格式化和可自动修复诊断，Prettier 负责 Markdown、JSON 和 CSS；两种格式化器按文件类型划分，避免同时改写同一文件。若不希望保存即格式化，则将 `editor.formatOnSave` 改成 `false`；显式保存时 ESLint 代码操作仍可按 `source.fixAll.eslint: explicit` 执行。不要添加 `"prettier.enable": false`，否则会关闭此处为 Markdown、JSON 和 CSS 指定的 Prettier 扩展。

设置项的作用：

- `eslint.useFlatConfig`：让 ESLint 扩展与 `eslint.config.js` Flat Config 配置配合工作。
- `eslint.validate`：指定编辑器中启用 ESLint 诊断的 JavaScript 和 TypeScript 文件类型。不要仅为 HTML/CSS 增加校验类型；只有 ESLint 已配置对应 parser 和规则时才添加。
- `editor.formatOnSave`：显式保存时运行当前语言的默认格式化器。
- `editor.codeActionsOnSave`：运行 ESLint 的自动修复；`source.organizeImports: never` 表示不自动重排导入。
- `editor.guides.bracketPairs`：显示括号配对引导线，帮助辨认 JSX、函数和条件分支的嵌套层级。
- `editor.tabSize` 与 `editor.insertSpaces`：统一使用两个空格缩进。
- 语言专属的 `editor.defaultFormatter`：JS/TS 使用 `dbaeumer.vscode-eslint`；文档、JSON 和 CSS 使用 `esbenp.prettier-vscode`。

操作步骤：

1. 安装并启用 ESLint、Prettier - Code formatter 两个 VS Code 扩展；团队也可以在 `.vscode/extensions.json` 中声明扩展推荐。
2. 检查项目根目录存在 ESLint Flat Config 和 `.prettierrc.json`，并已安装对应依赖；否则扩展没有项目规则可用。
3. 将上述设置保存到 `.vscode/settings.json`，而不是只保存进自己的 VS Code User Settings，这样团队成员可以共享设置。
4. 检查 `.gitignore` 是否忽略了 `.vscode/settings.json`。如果是，移除该忽略规则或添加对应例外，并把工作区设置提交到 Git。
5. 重启 ESLint 扩展或运行命令面板中的 **ESLint: Restart ESLint Server**，打开 JS/TS 文件并保存，确认格式修复生效；再保存 Markdown/JSON/CSS 文件，确认 Prettier 格式生效。
6. 如果没有生效，检查 VS Code“输出”面板里的 ESLint/Prettier 通道，并分别运行 `pnpm lint`、`pnpm format:check` 排查项目配置。

这些设置依赖 VS Code 扩展。其他编辑器的用户仍可通过 `pnpm lint:fix`、`pnpm format` 和 Git hooks 使用命令行质量检查。

## 五、端到端验证实施结果

### 步骤 12：依次运行全套检查

在项目根目录执行：

```bash
pnpm lint
pnpm typecheck
pnpm format:check
pnpm build
```

没有 TypeScript 的项目跳过 `pnpm typecheck`；没有构建脚本时跳过 `pnpm build` 并说明项目实际的交付验证方式。根据项目 package scripts 添加或调整命令，不要盲目复制不存在的脚本。

### 步骤 13：实际验证 Git hooks

创建一项小改动并将其加入暂存区：

```bash
git add <文件路径>
```

尝试错误的提交信息，确认 Commitlint 阻止提交：

```bash
git commit -m "update things"
```

使用合法信息提交，确认提交前暂存文件任务、类型检查及提交信息校验正常运行：

```bash
git commit -m "docs: 配置代码质量检查"
```

推送时确认 `pre-push` 构建检查运行。也可以仅用于本地验证地临时在 `.husky/pre-push` 中加入一个会失败的命令，并在验证后删除它。

运行钩子自动修复后，再检查工作区与暂存区：

```bash
git status --short
git diff
git diff --cached
```

这样可以发现自动修复引起但未预期的格式变更，并确认真正提交的差异。

## 六、日常执行清单

每个功能改动建议按以下顺序完成：

1. 按项目结构和命名约定编写代码。
2. 保存文件，让编辑器运行 ESLint 自动修复；检查编辑器显示的诊断。
3. 运行 `pnpm lint`、`pnpm typecheck`、`pnpm format:check`。
4. 手动验证受影响功能；如果项目有测试，运行相应测试命令。
5. 仅暂存本次相关文件，检查 `git diff --cached`。
6. 使用 `<type>(<可选 scope>): <主题>` 格式编写提交信息。
7. 提交时修复 hook 报出的错误，不要以跳过 hooks 作为常规工作方式。
8. 推送前确保生产构建和项目实际配置的测试均通过。

## 七、常见问题排查

### ESLint 在编辑器中没有诊断或保存修复

- 确认当前项目根目录下有 `eslint.config.js`，并已安装 ESLint 扩展和本地依赖。
- 查看 VS Code“输出”面板中的 ESLint 通道，确认扩展是否报错。
- 在终端运行 `pnpm lint`，排除 ESLint 本身配置错误。
- 确认当前文件类型出现在 `eslint.validate` 中，并且文件路径没有被 ESLint ignore。

### `lint-staged` 没有检查预期文件

- 确认文件已经运行 `git add` 进入暂存区；它只处理暂存文件，不会处理所有未暂存改动。
- 检查文件扩展名是否匹配 `lint-staged.config.cjs` 中的 glob。
- 确认 glob 对应的命令和 ESLint parser 确实支持这种文件类型。

### Husky hooks 没有运行

- 执行 `pnpm install`，确认 `prepare` 脚本执行成功。
- 执行 `pnpm exec husky`，确认 hooks 已启用。
- 检查 `.husky/pre-commit`、`.husky/commit-msg` 等文件是否存在且包含正确命令。
- 确认提交时没有使用跳过 hooks 的 Git 配置或环境变量。

### Prettier 和 ESLint 对同一行不断改写

- 确保 JS/TS 只由 ESLint 管理格式，Prettier 不要再格式化这些文件。
- 确保 `lint-staged` 的 JS/TS glob 和样式/文档 glob 不重叠。
- 统一提交 `.prettierrc.json` 和 ESLint 配置，让所有开发者使用仓库配置而非个人默认值。

### 构建或类型检查命令无法运行

- 查看 `package.json` 中真实的脚本名称。
- 确认 TypeScript 检查命令指向包含应用源码的配置文件。
- 将 hook 中的命令改成该项目实际存在的脚本；没有测试配置时，不要调用 `pnpm test`。

## 八、建议纳入版本管理的配置清单

```text
eslint.config.js
.prettierrc.json
.prettierignore
lint-staged.config.cjs
commitlint.config.cjs
.husky/pre-commit
.husky/commit-msg
.husky/pre-push
.vscode/settings.json       （团队使用 VS Code 时）
.vscode/extensions.json     （团队推荐扩展时）
package.json
pnpm-lock.yaml
```

所有质量规则应随项目代码一起提交并接受代码审查。新成员检出项目并执行 `pnpm install` 后，应能够运行相同的本地检查和 Git hooks；IDE 设置是协助，不应取代命令行检查和团队的功能验证流程。
