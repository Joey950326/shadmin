# 代码质量把控与开发体验

本文依据本项目当前的配置、脚本和目录结构，说明开发、提交和推送过程中的质量保障，以及开发工具的实际行为和可行的优化方式。文中会区分“项目已配置”和“建议做法”，避免把尚未启用的能力误认为自动化保障。

## 1. 质量保障概览

本项目使用 Vite、React 19 和 TypeScript。当前质量保障主要由以下环节组成：

| 环节       | 项目配置                                      | 检查内容                                  |
| ---------- | --------------------------------------------- | ----------------------------------------- |
| 编码与保存 | `.vscode/settings.json`、ESLint               | 编辑器 ESLint 集成、括号层级引导线        |
| 本地检查   | `package.json` scripts                        | ESLint、TypeScript 类型检查、生产构建     |
| 提交前     | `.husky/pre-commit`、`lint-staged.config.cjs` | 暂存文件修复/格式化、类型检查             |
| 提交信息   | `.husky/commit-msg`、`commitlint.config.cjs`  | Conventional Commits 格式及允许的提交类型 |
| 推送前     | `.husky/pre-push`                             | 生产构建                                  |

项目目前没有配置自动化测试框架或覆盖率门槛。因此，ESLint、类型检查和构建不能替代功能测试，受影响功能仍需要手动验证。

## 2. 开发过程中如何把控代码质量

### 2.1 遵守项目目录与命名约定

根据 `AGENTS.md`：

- 路由页面放在 `src/pages/`，可复用组件放在 `src/components/`，布局放在 `src/layout/`。
- 语言、主题、路由、状态等跨领域能力放在 `src/features/`。
- API 客户端、查询 hooks、keys 和类型放在 `src/services/api/`；路由定义放在 `src/routers/`。
- 新代码优先使用 TypeScript；从 `src/` 导入时优先使用 `@/` 别名。
- React 组件和组件文件使用 PascalCase；hook 使用 `use` 前缀；工具和配置模块使用 camelCase。
- 按功能归属组织代码；通用能力再放入公共组件目录，避免把功能逻辑无差别堆进通用目录。

这些约定让代码落在可预期的位置。ESLint 并不会自动检查所有目录归属和命名选择，开发者仍需遵守并在审查时确认。

### 2.2 利用 TypeScript 严格检查

`tsconfig.app.json` 和 `tsconfig.node.json` 开启了 `strict`、`noUnusedLocals`、`noUnusedParameters`、`noFallthroughCasesInSwitch` 等检查；应用侧检查 `src/`，Node 配置检查 `vite.config.ts`。修改后运行：

```bash
pnpm typecheck
```

类型报错应优先修复根因，不要为通过检查而随意扩大 `any`、移除必要类型或关闭编译器规则。需要验证完整生产构建时运行：

```bash
pnpm build
```

该脚本执行 `tsc -b && vite build`，会进行 TypeScript 项目构建并验证 Vite 生产构建。

### 2.3 利用 ESLint 统一编码规范

`eslint.config.js` 使用 `@antfu/eslint-config`，并启用 React 和 TypeScript 规则。显式配置的格式规则包括：2 个空格缩进、单引号、Stroustrup 大括号风格。

检查 ESLint 覆盖范围：

```bash
pnpm lint
```

自动修复 ESLint 可安全修复的问题：

```bash
pnpm lint:fix
```

`lint:fix` 会在 ESLint 检查范围应用 `--fix`，运行后请检查 `git diff`，确认没有引入无关变更。`src/components/ui/` 和 `src/components/diceui/` 被 ESLint 排除；根据 `AGENTS.md`，不要顺带重写这两个生成式 UI 目录中的代码。

### 2.4 建议的本地检查顺序

日常开发和提交前可运行：

```bash
pnpm lint
pnpm typecheck
pnpm build
```

如果修改业务或界面，还应手动操作受影响的路由；如果修改界面文本，按项目指南检查支持的两种语言。本项目没有测试运行器，不应假设 `pnpm test` 可用。

## 3. 提交时如何把控代码质量

### 3.1 提交钩子会执行什么

`package.json` 中的 `prepare` 脚本运行 `husky`。安装了 Git hooks 且提交时未跳过 hooks 的情况下：

1. **`pre-commit`：** 执行 `pnpx lint-staged`，然后执行 `pnpm typecheck`。
2. **`commit-msg`：** 使用 Commitlint 校验提交说明。
3. **`pre-push`：** 执行 `pnpm build`。

`lint-staged.config.cjs` 当前按暂存文件扩展名执行任务：

- `*.{js,jsx,ts,tsx}`：执行 `eslint --fix`。
- `*.{css,scss,less}`：执行 `eslint --fix`。
- `*.json`：执行 `prettier --write`。
- `*.md`：执行 `prettier --write`。

注意：以上仅表示配置的暂存文件任务，不代表所有文件都执行完整 ESLint、Prettier 或专门的样式检查。`pre-commit` 另行运行 TypeScript 类型检查。自动修复后仍应检查暂存区差异，确认改动符合预期。

### 3.2 统一提交 message

`commitlint.config.cjs` 扩展 `@commitlint/config-conventional`，并限制提交类型为：

| 类型       | 用途                         |
| ---------- | ---------------------------- |
| `feat`     | 新功能                       |
| `fix`      | 修复问题                     |
| `docs`     | 文档变更                     |
| `style`    | 代码格式调整，不涉及功能逻辑 |
| `refactor` | 重构                         |
| `perf`     | 性能优化                     |
| `test`     | 测试相关变更                 |
| `chore`    | 构建、工具等其他变更         |
| `revert`   | 回滚变更                     |

推荐格式：

```text
<type>(<可选 scope>): <简短、明确的主题>
```

示例：

```text
feat(auth): 增加登录验证码
fix: 修复登录布局背景颜色
docs: 补充代码质量把控说明
refactor(router): 简化动态路由处理
```

scope 可选，主题不能为空。配置禁用了 `subject-case` 检查，因此中文主题允许使用。主题应准确描述改动，避免只写“修改代码”“更新一下”等无法说明内容的描述。提交正文和破坏性变更说明可按需填写；提交前钩子校验最终提交信息。

### 3.3 推送前构建

`.husky/pre-push` 执行 `pnpm build`，因此推送前会检查 TypeScript 项目构建和 Vite 生产构建。该文件中的测试命令处于注释状态，不会执行。建议推送前另外运行 ESLint 和类型检查；有界面变更时完成手动验证。

## 4. 优化开发体验与代码格式

### 4.1 当前 VS Code 设置

仓库提供了 `.vscode/settings.json`，其中：

- `prettier.enable` 和 `editor.formatOnSave` 都是 `false`：当前没有启用 Prettier 默认格式化器，也没有启用编辑器的通用保存格式化。
- `editor.codeActionsOnSave` 将 `source.fixAll.eslint` 设为 `explicit`，因此显式保存时可触发 ESLint 修复；`source.organizeImports` 设为 `never`，不会自动整理导入。
- `editor.guides.bracketPairs` 为 `active`：编辑器会显示括号配对引导线，帮助辨认代码块嵌套层级。
- `eslint.useFlatConfig` 为 `true`，与项目 ESLint Flat Config 配置相匹配。

要让保存时确实执行 ESLint 修复，开发者本机需安装并启用 VS Code ESLint 扩展。仓库当前设置已经支持“显式保存时运行 ESLint 修复”，不等于 Prettier 格式化，也不保证每项修复都能自动完成。

### 4.2 推荐的保存时格式化方案

当前仓库没有 Prettier 配置文件；虽然依赖中安装了 Prettier 和 `prettier-plugin-tailwindcss`，项目 `format` 脚本的实际命令是 `prettier --write "**/*.{ts,tsx}"`，只覆盖 TS/TSX 文件。当前没有仓库级配置证明 Tailwind 插件已被加载，也没有配置统一的 Prettier 规则。建议不要直接启用 Prettier 格式化器并假设其格式与 ESLint 完全一致。

在现有规范下，最小化的体验优化是确认已安装 VS Code ESLint 扩展，并保留设置中的 ESLint 保存修复和括号引导线。若团队希望**保存时自动格式化**，先统一决定使用 ESLint 自动修复还是 Prettier 作为格式化器，再将选择写进仓库共享配置，避免不同开发者保存同一文件得到不同格式。启用编辑器保存时格式化的一个候选设置是：

```jsonc
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "dbaeumer.vscode-eslint",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit",
    "source.organizeImports": "never",
  },
}
```

以上是**待团队评估的建议配置，并非当前已启用设置**。ESLint 扩展是否能作为格式化器、具体支持哪些修复，取决于对应 ESLint 规则；合并配置前应在本项目实际验证。若改用 Prettier 格式化器，则需先补齐共享 Prettier 配置、Tailwind 插件加载方式和格式化文件范围，并协调 ESLint 规则，避免格式化规则互相覆盖。不要在未统一前同时启用两种竞争的格式化器。

### 4.3 手动格式化、括号引导线与代码块

项目现有 `pnpm format` 命令用于格式化 TS/TSX：

```bash
pnpm format
```

由于它会对 glob 匹配的文件执行写操作，使用前应检查工作区，使用后查看 `git diff`，尤其避免把生成式 UI 文件或无关文件的大面积变化混进功能提交。该命令不负责统一格式化 Markdown、CSS 或 JSON；这些类型仅在作为暂存文件提交时，才会匹配 `lint-staged` 中配置的 Prettier 命令。

代码块视觉层级方面，当前 VS Code 已启用括号配对引导线。建议保留 2 空格缩进、合理拆分过长的 JSX/函数，以及按项目目录和命名约定组织代码；ESLint 可统一其所支持的格式规则，但不会自动替代清晰的代码结构设计。

## 5. 推荐的团队开发流程

1. 使用 `pnpm install` 安装依赖；`prepare` 会安装/初始化 Husky hooks。
2. 开发时遵守项目目录、命名和 TypeScript 规范；在 VS Code 中启用 ESLint 扩展。
3. 修改后运行 `pnpm lint`、`pnpm typecheck`；有需要时运行 `pnpm lint:fix`，并审查修复差异。
4. 手动验证受影响路由与行为；界面文案变更按项目指南检查两种支持语言。
5. 仅暂存本次改动，按 `<type>(<可选 scope>): <主题>` 编写提交信息。提交钩子执行暂存文件任务、类型检查和 message 校验。
6. 推送前确认生产构建通过；`pre-push` 会运行 `pnpm build`。
